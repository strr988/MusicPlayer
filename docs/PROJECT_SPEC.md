## 1. Концепция продукта

### 1.1. Проблема

Современные музыкальные библиотеки разделены между стриминговыми сервисами и локальными файлами. Пользователи вынуждены переключаться между приложениями, мириться с ограничениями отдельных каталогов и использовать рекомендательные алгоритмы, не всегда соответствующие их предпочтениям.

Дополнительные проблемы — различия между версиями композиций, повторяемость рекомендаций, региональная зависимость подборок и ограниченный контроль над воспроизведением.

### 1.2. Цель

Разработать расширяемый музыкальный плеер с независимой библиотекой композиций, поддержкой различных источников воспроизведения и собственной адаптивной системой музыкальных рекомендаций.

### 1.3. Принципы проекта

- **Независимость библиотеки.** Композиции и плейлисты не должны быть жёстко привязаны к одному музыкальному сервису.
- **Модульность.** Источники музыки, воспроизведение, рекомендации и интерфейс разрабатываются независимо.
- **Контроль пользователя.** Пользователь управляет музыкальными предпочтениями и может отключать интеллектуальные функции.
- **Offline-first.** Основная локальная функциональность не требует постоянного интернет-соединения.
- **Прозрачность.** Приложение не должно скрывать источники композиций, собирать ненужные персональные данные или выполнять неразрешённые операции с контентом.
- **Развитие без переписывания.** Новые интеграции должны подключаться через определённые интерфейсы.

## 3. Технологическая архитектура

### 3.1. Рекомендуемый стек

| Уровень | Технология |
|---|---|
| Desktop | Electron |
| Интерфейс | React + TypeScript |
| Сборка | electron-vite |
| Стили | Tailwind CSS |
| Хранение данных | SQLite |
| Работа с метаданными | music-metadata |
| Аудиодвижок | HTMLAudioElement |
| Рекомендации | TypeScript, собственный алгоритм |
| Тестирование | Vitest |
| Репозиторий | GitHub |

**Почему Electron:** единый стек TypeScript, удобная интеграция веб-интерфейса с локальной файловой системой и быстрый старт для команды.

Tauri рассматривается как альтернатива в перспективе, но менять платформу посреди конференционной разработки нецелесообразно.

SQLite предполагается использовать через отдельный слой доступа к данным. Конкретный драйвер окончательно выбирается после проверки сборки Electron на Windows.

### 3.2. Основные подсистемы

**A. Desktop Shell**

Создание окна, системные диалоги выбора файлов, безопасное взаимодействие с операционной системой и упаковка приложения.

**B. Music Library**

Импорт композиций, чтение метаданных, организация библиотеки, поиск, плейлисты и хранение данных.

**C. Playback Engine**

Воспроизведение аудио, управление очередью, события начала и окончания трека, пауза и перемотка.

**D. Recommendation Engine**

Формирование персональной очереди с учётом предпочтений, истории и разнообразия.

**E. Source Adapters**

Общий интерфейс для источников. В версии 0.1 — адаптер локальных файлов. В дальнейшем — поддерживаемые внешние каталоги и сервисы.

**F. User Interface**

Отображение библиотеки, страницы «Волна», плеера, поиска и настроек.

### 3.3. Разделение ответственности

Electron Main Process отвечает за файловую систему, базу данных и защищённый доступ к локальному аудио.

React Renderer отвечает за интерфейс, управление воспроизведением и отображение состояния.

Обмен между ними осуществляется через ограниченный типизированный IPC-интерфейс.

Рекомендательный алгоритм разрабатывается как независимый модуль, который получает обычные данные о композициях и предпочтениях и возвращает упорядоченный список идентификаторов.

Это позволяет в дальнейшем использовать тот же алгоритм на других платформах.

## 4. Модель данных

Важно сразу разделить **композицию в библиотеке** и **источник её воспроизведения**.

### 4.1. Основные сущности

| Сущность | Основные поля |
|---|---|
| Track | id, title, artist, album, duration, genres, artwork |
| SourceItem | id, trackId, provider, providerId, localPath, availability |
| Playlist | id, name, createdAt |
| PlaylistItem | playlistId, trackId, position |
| PlaybackEvent | trackId, eventType, listenedDuration, timestamp |
| TrackPreference | trackId, liked, updatedAt |
| Settings | language, discoveryLevel, repeatPreference |

**Track** представляет конкретную запись композиции. Разные редакции одной песни пока не объединяются автоматически.

**SourceItem** указывает, где находится запись. У одного Track потенциально может быть несколько источников.

В будущем добавляется отдельная сущность MusicWork для группировки различных записей одного музыкального произведения.

Так мы сможем поддерживать оригиналы, ремастеры, концертные версии и цензурированные редакции, не усложняя первоначальную реализацию.

### 4.2. Правила хранения

- Оригинальные аудиофайлы пользователя не перемещаются и не изменяются.
- База данных содержит информацию о файлах, а не копии самих записей.
- Удаление композиции из библиотеки не означает удаление файла с диска.
- Недоступные файлы помечаются как отсутствующие.
- Персональные настройки и история хранятся локально.
- Схема базы данных версионируется через миграции.

## 5. Интерфейсы между модулями

До параллельной разработки нужно согласовать следующие операции.

| Операция | Результат |
|---|---|
| importFolder() | Список импортированных композиций и ошибок |
| getTracks() | Список Track |
| getTrackSources(trackId) | Доступные источники |
| getPlayableSource(trackId) | Разрешённый локальный аудиоисточник |
| recordPlaybackEvent(event) | Сохранённое событие |
| setTrackPreference(trackId, value) | Обновлённое предпочтение |
| generateWave(context, count) | Упорядоченный список Track ID |
| savePlaylist(playlist) | Сохранённый плейлист |

Названия предварительные. После утверждения они должны стать типизированными контрактами.

Главное правило: **модули не обращаются напрямую к внутренним данным друг друга**.

Например, рекомендатель не должен самостоятельно читать SQLite, а интерфейс не должен получать произвольный доступ к файловой системе.

Для воспроизведения локального аудио потребуется защищённый механизм выдачи медиаресурсов с проверкой разрешённых файлов.

## 6. Персонализированная «волна»

### 6.1. Цель алгоритма

Формировать непрерывную музыкальную очередь, которая постепенно адаптируется к пользователю и не повторяет слишком часто одни и те же композиции.

### 6.2. Входные данные

- Любимые композиции и исполнители.
- Музыкальные жанры, если они известны.
- История воспроизведения.
- Пропуски и дослушивания.
- Недавно воспроизведённые композиции.
- Желаемый уровень разнообразия.

Регион регистрации музыкального аккаунта не рассматривается как автоматический показатель предпочтений.

### 6.3. Первая версия алгоритма

Для каждой доступной композиции рассчитывается оценка на основе нескольких признаков:

1. Соответствие любимым жанрам.
2. Соответствие предпочитаемым исполнителям.
3. Положительные и отрицательные реакции.
4. Новизна композиции относительно истории пользователя.
5. Штраф за недавнее воспроизведение и частые пропуски.

Алгоритм выбирает композиции с высокими оценками, но часть очереди может отводиться новым, менее предсказуемым рекомендациям.

В первой версии используются эвристические веса, которые позднее можно корректировать экспериментально.

### 6.4. Холодный старт

Если история отсутствует, пользователь может выбрать несколько любимых жанров или композиций.

Если этих данных тоже нет, используется разнообразная очередь из локальной библиотеки.

Если жанры не указаны в метаданных, алгоритм не должен отказываться от рекомендаций — он использует другие доступные признаки.

### 6.5. Что исследуем

**Гипотеза:** адаптивная система рекомендаций повышает оценку соответствия вкусу по сравнению со случайным выбором и простой очередью по сохранённым лайкам.

Проверяем три алгоритма:

- A — случайная очередь.
- B — очередь по сохранённым лайкам с учётом исполнителей и жанров.
- C — адаптивная очередь с пользовательскими реакциями и контролем повторов.

**Метрики:**

- Доля положительно оценённых рекомендаций.
- Разнообразие исполнителей.
- Количество повторов.
- Количество пропусков.
- Время расчёта очереди.

Для сравнения используем одинаковый набор доступных композиций, небольшую группу добровольных слушателей и одинаковую методику оценки. Порядок предъявления подборок желательно менять, а их источник не раскрывать слушателю до оценки.

Результаты небольшой выборки рассматриваются как предварительные, без утверждений о превосходстве над коммерческими рекомендательными системами.

Формула первой версии, метод измерения и порядок пилота описаны в [документации «Моей волны»](PERSONAL_WAVE.md).

## 7. Пользовательский интерфейс

### 7.1. Основные экраны

**Библиотека**

Композиции, исполнители, альбомы, поиск, фильтрация, импорт файлов.

**Моя волна**

Крупная кнопка запуска персонального радио, текущая композиция, следующие рекомендации и элементы управления предпочтениями.

**Сейчас играет**

Обложка, название, исполнитель, полоса воспроизведения, управление очередью и лайками.

**Плейлисты**

Сохранённые пользовательские подборки.

**Настройки**

Музыкальные папки, поведение воспроизведения, параметры рекомендаций.

### 7.2. Визуальные принципы

- Современный, аккуратный интерфейс.
- Хорошая читаемость названий и исполнителей.
- Минимум отвлекающих элементов.
- Плеер доступен независимо от открытого экрана.
- Тёмная тема как первоначальный вариант.
- Без сложных анимаций, снижающих производительность.

Отдельно необходимо предусмотреть состояния загрузки, пустой библиотеки, ошибки чтения файла и отсутствующего аудиоисточника.

## 8. Критерии готовности версии 0.1

Прототип считается готовым к конференции, если:

- [ ] Приложение запускается на Windows.
- [ ] Пользователь может выбрать папку с музыкой.
- [ ] MP3 и FLAC с поддерживаемыми кодеками успешно импортируются и воспроизводятся.
- [ ] Композиции отображаются с доступными метаданными.
- [ ] Поиск находит треки в библиотеке.
- [ ] Работает управление воспроизведением.
- [ ] Работает последовательная очередь.
- [ ] Лайки и пропуски сохраняются.
- [ ] Персональная «волна» генерирует очередь.
- [ ] Изменение предпочтений влияет на последующие рекомендации.
- [ ] Библиотека сохраняется после перезапуска.
- [ ] Локальные композиции воспроизводятся без интернета.
- [ ] Исходные музыкальные файлы не изменяются.
- [ ] Подготовлен сравнительный эксперимент.
- [ ] Есть воспроизводимая инструкция запуска.

## 12. Основные риски

**Риск: проблемы с Electron и зависимостями.**  
Решение: проверить установку, запуск и упаковку в самом начале. Не усложнять проект необязательными нативными расширениями.

**Риск: недостаточно качественные рекомендации.**  
Решение: использовать прозрачный эвристический алгоритм и не требовать от него качества коммерческих рекомендательных систем.

**Риск: нехватка времени у команды.**  
Решение: независимые задачи, частая интеграция, резервная реализация через ИИ-агента.

**Риск: ограничения музыкальных сервисов.**  
Решение: не делать внешние стриминговые интеграции условием готовности версии 0.1.

**Риск: проблемы при демонстрации.**  
Решение: локальная музыкальная библиотека, работа без интернета, сохранённые результаты эксперимента и резервная видеозапись.

**Практический результат:** работающий прототип десктопного музыкального приложения с адаптивной очередью воспроизведения.

## 14. Критерий завершения проекта

Первая версия считается успешной, если разработана и проверена основная цепочка:

**Импорт музыки → Библиотека → Воспроизведение → Пользовательская реакция → Изменение рекомендаций.**

Это минимальный законченный сценарий, который демонстрирует одновременно программную реализацию и исследовательскую идею.

Остальные функции рассматриваются как развитие продукта, а не обязательные требования к конференционному релизу.
